# Agent Scaffold

> **在画布上画一个 agent，导出一个能独立部署的 agent 仓库。**
>
> 画布是**模具**，不是运行时 —— 导出的 agent 永远不依赖它。

---

## 这是什么

一个**可视化 AI Agent 编排平台**。在画布上拖节点、连线，每个节点用自己的话写
「这一步做什么」，AI 读懂描述后把参数补齐；点运行，逐节点看输入输出。

但产出物不是「一张图」，而是**一个完整的 agent 包**：定义、配置、业务工具、入口、
依赖清单与 Dockerfile 各就各位。它带走了同一份安全底座与执行引擎，
所以**离开画布也能独立跑**。

### 它要解决的问题

| 常见做法 | 这个项目的做法 |
|---|---|
| 每个 agent 各写一套底座，安全与工程能力靠抄、靠纪律对齐 | **一个底层实现「一份」**，所有 agent 从同一个模子压出来 |
| 平台跑 agent，agent 离不开平台 | **导出即独立** —— 本地、局域网、公网都能部署 |
| 「相似」的底层，靠文档维持一致 | 「**同一个**」底层，靠**封条**与 CI 门禁证明，不靠承诺 |

---

## [核心主张] 画布是编辑器，LangGraph 是执行引擎

> 节点写共享状态 `vars[node_id]`，**边只表达依赖**。
> 所以画布上的一条连线不会变成一句代码，而是变成一次**状态写入**。

这一条决定了几乎所有设计：为什么加一种节点类型前端零改动、为什么分支节点要真正执行、
为什么多条边进同一个 handle 要收成列表。

## 三层，以及两个时间

架构图最容易画错的地方，是把它画成一个「平台 ⇢ agent」的**依赖**箭头。**恰好相反。**

```
【构建时】只发生一次，之后画布离场

   ┌────────────────────────────────────────────┐
   │ 层 1 · 画布平台（本仓库）                    │
   │  前端 / app/api/ / app/main.py / app/db/     │
   │  职责：画图 · AI 补齐 · 调参 · 试跑 · 导出     │
   └────────────────────────────────────────────┘
              │ 导出（写文件）
              ▼
   ┌────────────────────────────────────────────┐
   │ 层 3 · agent 包（交付物）                    │
   │  定义 + 配置 + 业务工具 + 入口 + 依赖清单      │
   └────────────────────────────────────────────┘

【运行时】画布（层 1）一条箭头都不出现在这里

   main.py ──import──► 层 2 · runtime 包
      │                  安全底座 · 执行引擎 · 能力接口
      │                        │
      └── 读 agent 自己的      └──import──► LangGraph / httpx / 标准库
          定义 · 配置 · 业务工具
```

**「层 1 在运行时一条箭头都没有」，就是「导出的 agent 永远不依赖画布平台」的技术含义。**

| 层 | 是什么 | 交付形态 |
|---|---|---|
| 1 · 画布平台 | 模具旁边的**试模机** | 只有人用 |
| 2 · runtime 包 | **模具**（一份） | 层 3 的 `main.py` **依赖**它，不是拷贝它 |
| 3 · agent 包 | **压出来的零件** | 交付物 |

### 不变量 vs 变量

| 永远一致（不变量 · 一份实现） | 每个业务不同（变量 · 适配时改） |
|---|---|
| 执行引擎（编译 / 调度 / 恢复） | **图本身**（节点与边） |
| 沙盒机制（怎么隔离、怎么限内存） | 沙盒**档位**（本机子进程 / 容器） |
| 出网机制（怎么做地址校验） | **允许访问哪些主机** |
| 认证机制（怎么校验、怎么哈希） | 这个 agent 的凭据 / 入口策略 |
| 事件流 · HITL · 重试 · 超时**机制** | 具体数值 |
| 图编译器 · 节点执行框架 | **业务工具**（它自己的 API / 库客户端） |
| 脱敏 · 序列化 · 生命周期 | 用哪个模型、提示词、表达式 |

> 左列的**实现**是共享的一份；右列才是「每个客户改的那点东西」。

## 三条约束（每条对应一个具体会发生的失败）

**① 画布跑的运行时 = 导出后跑的运行时，同一份代码。**
不能是「相似的」，更不能是「导出时裁剪过的子集」。
反例：导出物若用另一份编译器，「节点超时」在画布上测试通过，交付后那条路径**没有超时** ——
节点卡死就永久卡死，而测试记录上写着「已验证」。

**② 平台依赖 runtime，不能包含它。**
否则就有两份，必然漂移；漂移之后「相同底层」变成「**曾经**相同」。

**③ 导出路径必须从第一天就在**，而不是收尾工作。
独立性必须被**持续验证**，而不是日后审计。

> 这三条的落实方式（声明 + 随包 + 封条 + CI 门禁）→ [`docs/target/delivery.md`](docs/target/delivery.md)

## 架构速览

### 单一事实源

```
backend/app/graph/schema.py  (Pydantic)
        │
        ▼  GET /api/node-types
frontend/src/types/workflow.ts   (TS 镜像)
        │
        ▼
通用渲染：NodePalette / Inspector / SchemaForm
```

前端**没有任何按节点类型定制的渲染代码** —— 表单完全由后端的 `ParamSpec` 判别联合驱动。
**加一种节点类型 = 只改后端一个文件，前端零改动。**
代价是 TS 镜像是手工维护的，会静默漂移。

### 节点系统

**16 种节点，全部实测可跑**，注册表驱动。逐节点的参数与关键点 →
[`docs/reference/backend-layers.md`](docs/reference/backend-layers.md) §2

> 注意：`retriever` 是 **BM25，不是向量检索** —— 它无法匹配同义词（「车」vs「汽车」）。

### 能力层（架构心脏）

「一个底层」的**物理形态**。统一形状：

```
ABC + 默认实现 + 进程级 get_*/set_* 注入点 + 从 Settings 构造的 build_*
```

**为什么必须是接口，而不是「在每个节点里写 if」**：加一个新节点类型就要重新想一遍
所有横切关注点 → **必然遗漏**；想从本地切到生产 → 要改 N 个地方，且没有编译器帮你检查。

### 一次运行的数据流

```
POST /api/runs
      ▼
RunManager.create()   ← 编译图（失败 → HTTP 422，用户看得到）
      ▼
compiler 的 _make_node_fn（每个节点一个闭包）
      ├─ 收集 inputs（读前驱的 vars）
      ├─ emit("node_started")
      ├─ await run_with_policy(...)     ← 超时 / 重试
      ├─ 结果写进 vars[node.id]
      └─ emit("node_finished")
      ▼
EventBus.emit() ──► SSE 订阅者（重放 + 增量）──► 前端投影到节点卡片
      ▼
_run 结束 → _persist_finish() → _retire()
```

> **顺序是有意义的**：`_persist_finish` 必须在 `_retire` 之前 —— 前者要读事件历史，
> 后者会裁掉它。调换这两行，每次长运行的开头都会从记录里消失。

## AI 能力

**六个功能**，围绕「让画布听懂人话」：

| 能力 | 作用域 |
|---|---|
| **填参数** | 单节点 —— 描述里没写全的参数，AI 补齐 |
| **生成工作流** | 整图，从零或追加 |
| **修复工作流** | 整图，**只修错误** |
| **配置 ⇄ Python** | 单节点，Code 节点的双向转换 |
| **起名** | 单节点 |

**只有「AI 修复」能看到校验结果** —— 因为它的完成判据就是「校验通过」。

### 绝不静默改画布

所有功能一律返回 **diff**，等用户 Accept / Reject；生成整图也是先给草稿做预览覆盖层。
**原因**：静默改画布 = 图不可预测，与可视化编辑器的目的相反。

`修复` 与 `生成` 是两件事：前者**最小修正**，后者**重新生成**。

### 三重护栏：防止「删光就没错」

一个只会删节点的修复器能「修好」任何图。所以有三重护栏卡住它 ——
完成判据、结构性约束、以及可测性（把「信任决策」从「驱动模型」里拆出来单独测）。

→ 细节见 [`docs/current/ai-features.md`](docs/current/ai-features.md)

## 交付物：导出的 agent 长什么样

**这是一个独立的 git 仓库**，客户能读、能改、能 `docker build`。

> 下面是**完成态**的定义。逐项的当前状态（例如 `config/*.yaml` 尚未生成）
> → [`docs/target/delivery.md`](docs/target/delivery.md) §1。

```
my-agent/
├── agent.yaml          图 + 业务逻辑（逻辑用 !ref 外置）
├── agent.lock          版本锁定：runtime / 镜像 digest / 图哈希 / 子图版本
├── prompts/            提示词独立成 .md，片段可被多处引用
├── code/               代码节点独立成 .py（可单测、可 IDE 检查）
├── tools/              [重要] 业务工具 —— 客户接口适配的主场
├── config/             [重要] 客户改的配置
│   ├── .env.example        接口地址 / 密钥名（**值绝不进包**）
│   ├── models.yaml         用哪个模型、温度、超时
│   ├── limits.yaml         预算 / 超时 / 重试 / 并发
│   └── capabilities.yaml   能力开关盘
├── tests/              客户改完能自己验证
├── main.py             入口
├── requirements.txt    runtime 依赖（带**哈希封条**）
├── vendor/             runtime 的 whl（离线可装）
├── Dockerfile          多阶段构建
└── README.md           怎么跑 / 改 / 调 / 升级
```

### 四种触发方式（`main.py` 的 CLI）

| 命令 | 用途 |
|---|---|
| `run` | 命令行单次跑（调试 / 批处理） |
| `serve` | **HTTP 服务** |
| `schedule` | 常驻，按时 / 事件唤醒 |
| `migrate` | 建 / 升级它自己的表 |

### 「相同底层」怎么变成事实

**声明 + 随包 + 封条**，三者缺一不可：runtime 的每条依赖都带 `sha256`，
导出器把它抄进 agent 的 `requirements.txt`，客户用 `--require-hashes` 安装。
**封条一破，安装就失败** —— 一致性不再依赖信任。

> **这里不写命令，也不写数字 —— 是故意的。**
> 这个仓库的文档有一条硬规则：**每个事实只有一个归属地**，

## 这个仓库的文档纪律

文档不是事后补的说明，是**工程的一部分**。三条规则决定了它们长什么样：

1. **事实只写一处** —— 别处链接过去。重复的事实就是会漂移的事实。
2. **过期就删**，不留「已被取代」的横幅 —— 半死半活的文档让读者必须处处提防。
3. **时间快照必须显式标注** —— 没标注的默认是现状，这最容易误导人。

以及一条工程规则：**新加一个守卫，必须证明它会红。**
一个从没失败过的测试，可能只是装饰品。
