# 第一部分 · 已做的决策

## 架构与实现

| 决策 | 选择 | 理由 |
|---|---|---|
| **隔离强度** | 子进程为默认，容器为生产 profile | 容器每 run 启动 100ms–1s 会毁掉交互式节点调试；子进程拿 95% 安全性、5% 成本。**不可信来源强制容器** |
| **队列** | 先用 Postgres `SKIP LOCKED`（不引入新依赖） | 升级路径留 Redis |
| **存储** | SQLAlchemy 已就位（SQLModel）→ 加 alembic；Postgres 生产默认、SQLite 开发默认 | |
| **认证** | 不透明 bearer token（哈希存储 + scope），**默认要求** | 见 [`../current/security.md`](../current/security.md) |
| **记忆** | pgvector 生产 / SQLite FTS 本地回退 | 保证本地零依赖仍可跑 |
| **迁移策略** | **绞杀者模式**，不推倒重来 | 现有脚手架保持可用，能力层从底下长出来，节点逐个迁移 |
| **平台形态** | 统一 runtime 包 + agent 独立部署 | 用户原话「是都一样，不是都跑在一个上面」 |
| **图组合** | **引用 + 版本锁定**（不是内联展开） | 内联展开等于把「改一处改 N 处」换个地方；引用需要版本化，所以任务 28 随之提前 |
| **产出物分级** | 画布 → **定义**；runtime 包 → **agent** | 这个区别写不清，就会把「导出一份 JSON」误认为「导出 agent」 |
| **交付机制** | **声明 + 随包 + 封条**（`==1.2.0` + `vendor/*.whl` + `--require-hashes`） | 让「相同底层」从**承诺**变成**安装时强制校验的事实**。Docker 项目里更干净：runtime 做成基础镜像 |
| **runtime 边界** | 平台 **依赖** runtime，runtime **不依赖**平台 | 方向反了就有两份，必然漂移。当时 `manager.py` 的 `from app.db` 就是反的 —— **已解**（任务 2.6 + 27a），现由 AST 门禁守住 |
| **独立性验证** | **CI 从第一天就跑「导出后在空环境启动」** | 独立性必须被持续验证，而不是日后审计。缺了这一步，平台假设会长进去 |
| **适配改什么** | 接口（业务工具）+ 配置 + **业务逻辑** —— 都是**变量** | 交付物必须是一个客户工程师**能读能改**的普通代码项目 |
| **导出怎么做** | 逻辑**外置成文件**（`prompts/*.md` · `code/*.py`），配置进 `config/*.yaml`，密钥**值绝不进包** | JSON 里转义的字符串客户改不动；逻辑外置后 git diff 看得清改了哪句 |
| **`trusted` 标记** | 导出时**重新显式确认**，不继承 —— [重要] **尚未实现** | 画布上的 `trusted` = 「开发者接受以自己身份跑」；交给客户是另一件事。代码里还没有这一步：`export.py` 只做凭据遮蔽，`trusted` 原样写进导出物。见 [`../reference/design-decisions.md`](../reference/design-decisions.md) §安全 |

# 第二部分 · [重要] 待决（NEEDS DECISION）

> **不要自行假设，也不要在没有答案时按某一侧实现** ——

## 待决 1 · `agent.yaml` 是**权威**还是**派生物**？ → [x] **已定（2026-10-08）：B · 导出即源码**

**决定**：交付物是**源码形态**——逻辑外置成 `prompts/*.md` 与 `code/*.py`，
定义以引用（`$ref` / 未来的 `!ref`）指向它们。**源码是运行权威**，客户改的是普通文件。

**接受的代价**：往返画布**有损**（`node_to_code` / `code_to_node` 会报 `lossy`），
即客户改完的源码不保证能无损读回画布。这是选 B 换来的「客户能读能改」的代价。

**已实现**（任务 29，2026-10-08）：定义本体已是 **`agent.yaml` + `!ref`**（YAML 标签 +
消费端 `add_constructor`）、逻辑外置（`prompts/*.md` / `code/*.py`）、`manifest.yml`。
**仍开**：`config/capabilities.yaml`、`models.yaml`、`prompts/partials/`、lock 的镜像 digest，
以及**哈希未覆盖外置文件**（客户改 `prompts/*.md` 不会被 selfcheck 发现）。

### 问题

客户适配时「改业务逻辑」，改完还能不能拿回画布？

| | A. 定义驱动 | B. 导出即源码 |
|---|---|---|
| 交付物 | `agent.json` | **一节点一文件的 Python 模块** |
| 改逻辑 | 改 JSON 字符串（转义、难读） | 改普通 Python 文件 |
| 画布还能往回改 | [x] 定义是权威 | 注意： 往返**有损** |
| 现状支持 | 已有 `node-to-code` / `code-to-node`，**且会报 `lossy`** | 同左 |

### 影响

| 影响什么 | 怎么影响 |
|---|---|
| 交付物第 1/4/5 项的形状 | `agent.json` vs `generated/*.py` |
| §「导出流程」的第 2/3 步 | 冻结版本 vs 生成源码 |
| 门禁第 ⑤ 条 | 断言的是 JSON 还是源码 |
| **要不要修 `api_key` 明文落盘** | 若 JSON 是灾备副本 → 保留真值合理；若要交付客户 → **必须遮** |
| 客户改完能否回画布 | A 能，B 不能（或需有损往返） |

### 当前的判断（**未确认**）

客户工程师要能「改业务逻辑」，听起来更像 **B**（导出即源码）；
但「改完还能回画布」是 A 才有。

**这两条要求同时成立的话**，需要的是
「**源码为运行权威 + 定义保留用于回读**」—— 那是一个**更复杂的设计**。

→ **所以更要先定，不要边写边猜。**

## 待决 2 · 上门部署的是**谁的工程师**？

### 问题

是我们的人，还是客户的？

### 影响

| 影响什么 | 我们的人 | 客户的 |
|---|---|---|
| runtime 交付方式 | [x] 可依赖**私有包源** | [ ] 不行 → 必须**随包**（vendor / 基础镜像） |
| 客户能否改 runtime | 不需要 | **要预设他们会改** → 那就必须能验证哈希 |
| CVE 补丁责任 | 我们 | 要交接流程 |
| 文档要写什么 | 内部部署手册 | 「runtime 升级流程」面向客户的说明 |

### 为什么重要

它决定「相同底层」是**一份代码**（物理上就是同一个）
还是**N 份必须同步的拷贝**。

## 待决 3 · 图组合的实现深度

### 问题

只做「一图嵌一图」，还是要更多？

| 深度 | 内容 | 工作量 |
|---|---|---|
| **最小** | 引用一个子图，固定端口映射 | 小 |
| **中** | + 端口映射可配 + 参数化（同一子图不同参数多处实例化） | 中 |
| **深** | + 子图内可视编辑 + 引用关系图 + 影响分析 | 大 |
