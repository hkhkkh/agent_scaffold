# 愿景与产出物定义

---

## 1. 用户的原话

> 「这个脚手架，提前搞好了要做的 agent 的所有的底层，比如安全，工程，并发，性能，
> 沙盒这种的等等的一切，**所有做出来的 agent 都是这一个底层框架**，
> 并且我想让它能够做出来的 agent 是完整的，完善的，包括你刚才说的
> 可以长时间琢磨，长期记忆的自主的，还有其他的一切的东西」

补充约束（决定了几乎所有架构选择）：

| 问题 | 回答 | 翻译成架构约束 |
|---|---|---|
| 部署形态 | 「可以导出成完整的独立使用，可以本地，可以局域网，可以公网」 | **默认安全**；本地只是「显式关闭」，不是「没有」 |
| 隔离强度 | 「应该怎么做最好就怎么做」 | 按最佳实践，不为省事留技术债 |
| 自主性 | 「市面上的 agent 是什么样的就怎么样」 | 对标 LangGraph Platform / OpenAI Assistants / Devin |
| 平台形态 | 「**是都一样，不是都跑在一个上面**」 | [重要] **统一底层，但每个 agent 是独立可部署单元** |
| 持久化 | 「企业生产级的」 | Postgres + 迁移，真持久化 |

### [重要] 后面澄清的两句（最重要）

> 「每一个制作出来的 agent 都是相同的底层架构，安全一类的，当然要根据实际业务
> 改一些东西，但是基本一致，**因为都是从画布制作出来的 agent**」

> 「**导出的 agent 在运行时应该永远不依赖这个画布平台**，应该能独立完整运行，
> 有自身的安全底座和运行框架，里面有业务处理逻辑和代码，
> **他是完整的，不是只有点和边的关系**」

## 2. [重要] 画布是 agent 的模具

**一个底层（执行引擎 + 安全底座）实现「一份」，所有 agent 从同一个模子压出来。**

所以底座必然一致 —— **不是「相似」，是「同一个」**。

| | 说明 |
|---|---|
| **在画布里也能跑** | [x] **应该的**，那是开发闭环（画完立刻试、改完立刻再试）。**不是限制** |
| **导出后** | 永远不需要画布，因为它带走的就是那份底层 |
| **每个 agent 不同的部分** | 图 · 业务逻辑 · 业务工具 · 能力开关（"根据业务改的那些"） |

### 不变量 vs 变量

| 永远一致（不变量 · 一份实现） | 每个业务不同（变量 · 适配时改） |
|---|---|
| 执行引擎（编译 / 调度 / 恢复） | **图本身**（节点与边） |
| 沙盒机制（怎么隔离、怎么限内存） | 沙盒**档位**（本机子进程 / 容器） |
| 出网机制（怎么做地址校验） | **允许访问哪些主机** |
| 认证机制（怎么校验、怎么哈希） | 这个 agent 的凭据 / 入口策略 |
| 事件流 · HITL · 重试 · 超时**机制** | 具体数值 |
| 图编译器 · 节点执行框架 | **业务工具**（它自己的 API / 库客户端） |
| 脱敏 · 序列化 · 生命周期 | 用哪个模型、提示词、表达式 |

> 左列的**实现**是共享的一份；右列才是「每个客户改的那点东西」。
>
> 所以「今天一个进程 = 一个能力档位」说的不是「要给每个 agent 加一份配置」，
> 而是：**右列本来就该是每个 agent 包的一部分**。今天它被焊成了全局的。

## 3. [重要] 三层，以及三个箭头分别是什么意思

原路线图的架构图**是错的** —— 它画了一个「平台 ⇢ agent」的箭头并标上「依赖」，
读起来就是「agent 依赖平台」。**恰好相反。**

正确的形状分**两个时间**：

```
【构建时】只发生一次，之后画布离场

   ┌────────────────────────────────────────────┐
   │ 层 1 · 画布平台（本仓库）                    │
   │  前端 / app/api/ / app/main.py / app/db/     │
   │  职责：画图 · AI 补齐 · 调参 · 试跑 · 导出     │
   └────────────────────────────────────────────┘
              │ 导出（写文件）
              ▼
   ┌────────────────────────────────────────────┐
   │ 层 3 · agent 包（交付物）                    │
   │  定义 + 配置 + 业务工具 + 入口 + 依赖清单      │
   └────────────────────────────────────────────┘

【运行时】画布（层 1）一条箭头都不出现在这里

   main.py ──import──► 层 2 · runtime 包
      │                  安全底座 · 执行引擎 · 能力接口
      │                        │
      └── 读 agent 自己的      └──import──► LangGraph / httpx / 标准库
          定义 · 配置 · 业务工具
```

### 三个箭头的准确含义

| 箭头 | 是什么 | 什么时候 |
|---|---|---|
| 画布 ──► agent 包 | **写文件**（导出） | 构建时，一次性 |
| `main.py` ──► runtime 包 | **import**（依赖） | 每次启动 |
| runtime 包 ──► LangGraph 等 | import | 每次启动 |

> **「层 1 在运行时一条箭头都没有」，就是「导出的 agent 永远不依赖画布平台」
> 这句话的技术含义。**

### 「相同底层」= 一份实现，不是 N 份相似实现

| 层 | 是什么 | 谁 import | 交付 |
|---|---|---|---|
| 1 · 画布平台 | 模具旁边的**试模机** | 只有人用 | [ ] |
| 2 · runtime 包 | **模具**（一份） | 层 3 的 `main.py` | [x] 一份（依赖，非拷贝） |
| 3 · agent 包 | **压出来的零件** | 交付方运行 | [x] 交付物 |

### [重要] 层 2 的边界**不是按目录切的**

**原来的 `app/ai/` 是混的** —— 8 个文件里 3 个是运行时、5 个是构建时，
却同放一个目录。（任务 27a 之后这个目录**已不存在**：进包的在 `app/runtime/ai/`，
不进包的在 `app/ai_buildtime/`。逐文件的归属表 →
[`../current/files.md`](../current/files.md) §「`app/ai/` 已按依赖切开」。）

`repair-graph` 是「修画布上的图」的能力，**导出的 agent 不需要它**。

> 所以**任务 27a 不是 `git mv`，是真的分层** —— 目录边界和架构边界不重合。

`security/deps.py` 同理：它是 FastAPI 中间件（`app/main.py` 才用它），
属**层 1**。而 `auth.py` 是纯标准库（hashlib/hmac/secrets），属**层 2**。

## 4. 运行时几乎已经可分，只有一处耦合（已解 2026-09-14）

实测导入（`grep '^from fastapi|^from sqlmodel'`）：

```
from fastapi  → 只在 api/*.py 与 main.py             ← 层 1 独有
from sqlmodel → 只在 db/*.py 与 scheduling/store.py  ← 层 1 独有
```

**好消息**：`runtime/sandbox.py` 和 `security/auth.py` 是**纯标准库**（能原样跟着走）；
`nodes/*.py` **零个 `app.db`**。

### [重要] 唯一的反向依赖（已解）

`manager.py` 一度把「编排」和「运行历史落库」混在一起 —— 于是运行框架
`from app.db import ...`，**方向反了**：`pip install runtime` 会把平台一起拖进来，
导出物被迫打包平台，正是本文档要排除的情况。

**修法**：给运行历史加能力接口 `RunStore`（SQLite / Postgres / 内存 / **不记录**）
→ 已解决（2026-09-14，任务 2.6）：[`../log/phase-2-4-run-store.md`](../log/phase-2-4-run-store.md)

## 5. [重要] 三条约束（每条对应一个具体会发生的失败）

### 约束 1 · 画布跑的运行时 = 导出后跑的运行时，**同一份代码**

**不能是「相似的」，更不能是「导出时裁剪过的子集」。**

**反例**：假设导出物用另一份编译器，那么「节点超时」在画布上测试通过
（[x] 卡死被砍掉），交付后**那条路径没有超时** —— 节点卡死就永久卡死，
而测试记录上写着「已验证」。

**安全上更要命**：AST 守卫验过的是**画布那条路径**，另一条可能是裸的。

### 约束 2 · 平台**依赖** runtime，不能**包含**它

否则就有两份，必然漂移；漂移之后「相同底层」变成「曾经相同」。

§4 那个 `manager.py` 的反向依赖就是这个方向错了的证据。

### 约束 3 · 导出路径必须**从第一天就在**（而不是收尾工作）

那行 `from app.db import` 不是谁偷懒写下的 —— 是**当时唯一的消费者就是平台**，
而平台有数据库，所以它长得毫无阻碍。

如果从第一天就有一个 CI 任务「**导出 agent，在空 venv 里跑起来**」，
它写下的当天就会红。

> **独立性必须被持续验证，而不是日后审计。**

→ 这三条的具体落实（声明 + 随包 + 封条 + CI 门禁）
→ [`delivery.md`](delivery.md)

## 6. [重要] 根本张力：这不是加功能，是换执行模型

现在的模型是：

```
调用一次 LangGraph → 跑完就结束
```

「长时间琢磨 + 长期记忆的自主 agent」需要的是：

```
常驻 → 可被唤醒 → 能睡能醒 → 记得住上个月的事
```

**这是两种执行模型**，不是同一模型的功能增强。需要三样当时**完全没有**的东西
（**均已于 Phase 2–4 落地**，记为历史对照）：

1. **持久化执行**（重启不丢）—— [x] 任务 14 / 14b，默认 sqlite
2. **调度器**（没人驱动时也能跑）—— [x] 任务 22（定时 + 事件唤醒）
3. **记忆分层**（工作 / 情景 / 语义）—— [x] 任务 19（`langgraph.store` 三层 + 向量检索）

> 任何试图「在现有 run 循环上打补丁」来实现自主 agent 的方案都会失败，
> 因为现有循环的**生命周期假设就是错的**。
