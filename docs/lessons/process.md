# 方法论教训

> 这些不是「某个 bug 的修法」，是**「怎么会犯这类错、怎么不再犯」**。
> 每一条都真实浪费过大量时间。

---

<a id="p1"></a>

## 1. [最重要] 写守卫必须反向验证

### 规则

写完任何守卫（校验、检查、护栏），**必须**故意制造一个它该抓的错误，
**确认对应测试真的报 FAIL**，再恢复。

### 为什么

**「检查全绿」不代表「检查有效」。** 一个永远返回 True 的守卫
和一个正确的守卫，在正常情况下**看起来完全一样**。

### 本项目因此抓到的 5 次严重问题

| # | 是什么 | 性质 |
|---|---|---|
| 1 | AI 修复的 4 个护栏里 **2 个完全没被测试覆盖** | 守卫没被验证 |
| 2 | **「认证中间件没挂上」** —— 控制逻辑正确、测试充分、**但产品里没启用** | 最危险的一类 |
| 3 | 沙盒的 `__import__` 被 blocklist 误删（**先前就存在的 bug**） | 守卫被自己删了 |
| 4 | 抽 `SandboxRunner` 时：内存上限根本传不进去、`MemoryError` 消息是空的、容器入口缺 `sys.path` 注入 | 三个真 bug |
| 5 | 抽 `ToolRegistry` 时：注册表在 import 时被冻结、`fail_on_error` 被绕过、**`unknown_tool_names` 自己就是装饰品**，以及**我虚构了一个不存在的守卫** | 前提是错的 |

### [重要] 第 5 次是最特别的一次

我假设「节点直接 import 模块函数 = **绕过了接口**」，然后写了守卫去测它。

**反向验证报 `not caught`** —— 因为**那个风险不存在**：
模块级函数本来就代理到同一个注册表，所以
`get_tool(name)` 和 `get_tool_registry().get(name)` **行为完全相同**。

> **所以反向验证的作用不只是「查覆盖」** ——
> **它还会证伪你自己的假设。**

**判据**：写守卫前先问「**这个风险真的存在吗**」。

→ 完整故事：[`../log/phase-1-2-tools.md`](../log/phase-1-2-tools.md)

## 2. [最重要] 不可证伪的测试 = 永远绿的装饰品

### 症状与判据

反向验证报 `not caught` 时，有**两种完全不同的原因**：

| 原因 | 处理 |
|---|---|
| 产物没 bug | [x] 正常，说明守卫不必要 |
| **测试不可能失败** | [ ] **必须修测试** |

**把第二种当成第一种，就得到一个永远绿的套件。**

**判据**：先问「**这个测试有没有可能失败**」，
以及「**让它失败需要改哪个东西**」。

### 本项目抓到的五个真实例子

| 测试 | 为何无法失败 | 修法 |
|---|---|---|
| `test_describe_covers_every_known_secret` | `KNOWN_SECRETS` 只有**两个**成员 —— 覆盖循环要有**多于一个名字**才说明得了问题（否则「只返回第 0 个」和「返回全部」分不出来） | 测试里 monkeypatch **再追加一个**名字（`future.second_key`，凑到第三个） |
| `test_an_empty_string_counts_as_absent` | `get()` 已经把 `''` 归一成 `None`，所以去掉 `has()` 的 strip **不改变结果** | 指向 `test_whitespace_also_counts_as_absent`（`'   '` 是 truthy） |
| SSE 回放窗口测试 | 断言「响应头 == `bus.earliest_seq`」—— 把 `earliest_seq` **硬编码成 1**，两边一起错，测试照样绿 | 锚定**实际保留的事件序号**（`history()[0].seq == reported` 且 `reported > 1`） |
| HITL「只暂停一次」（任务 18） | 数的是 `INTERRUPT_RAISED` **事件**，而 manager 每次 `ainvoke` **只发一个** → 事件数恒为 1，有没有守卫都一样 | 改数**节点进入次数**（探针量出无守卫时是 4 次） |
| 「凭据不会进 step payload」（任务 2.6） | 节点的 `model.api_key` **根本不在 step payload 里**（配置走事件，不走 step）→ 断言恒真 | 改成构造**嵌套的凭据键**（`{"api_key": ...}`），那才是遮蔽真的会处理的东西 |

> **同一类错误在本项目犯了两次**（任务 18 和任务 2.6），
> 而且**两次都是反向验证抓到的** —— 我自己写完时都以为测试是有意义的。
>
> 结论：**「先问这个测试有没有可能失败」不能靠记性，要靠工具。**
> 每写一个守卫就同时写一条反向验证用例，是唯一可靠的执行方式。

### [重要] 一个更隐蔽的形态：比较的两边来自同一个源

**那不是在比较。** 让任何一边错，另一边跟着错，测试永远绿。

**推广**：一个比较，只有在你**故意让它漏看**会失败时，才算在比较。

→ 这个原则也用在了数据库迁移的「双路径一致性守卫」上：
[`../log/phase-2-1-alembic.md`](../log/phase-2-1-alembic.md)

### 一个生产性用法：拿它去找真 bug

任务 2.6 时，正是因为要把「读出运行历史」的两条路径收到一个接口后面，
才不得不问「**这两条路径会不会不一样**」——
于是发现了「实时读遮蔽、落盘不遮蔽」（[`backend.md#b16`](backend.md#b16)）。

> **「这里是不是有第二条路」是一个能主动去找 bug 的问题**，
> 不只是写完测试后的自查。

## 3. [最重要] 探针被中断 → **先恢复，再跑测试**

### 规则

反向验证脚本（`_guardprobe_*.py`）被中断后：

```powershell
Set-Location h:\agent_scaffold\backend
& 'd:\AI_LLM_Project\venv_d\Scripts\python.exe' _restore_guardprobe.py
# 必须看到 RESULT=CLEAN（INCOMPLETE ≠ 干净）
# 然后再跑 pytest
```

**顺序反了就会拿变异状态当基线。**

### 为什么

`_guardprobe_*.py` 在 `finally` 里恢复源文件 —— 但 **SIGKILL 不执行 `finally`**。

一次被中断后，变异 `chosen = "inprocess"` **留在了 `sandbox.py` 里** ——
之后所有沙盒测试都走进程内路径（**没有内存限制、死循环杀不掉**）。

而**当时这个仓库还没有 git**，那份变异差点变成「永久」。

### [重要] 更可怕的：变异是「语法合法、功能静默降级」

那个变异恰好是「某条分支改成 `if False`」这类改动 ——

**`pytest` 会照常报绿。**

（这正是反向验证脚本的设计意图：让测试在变异下失败。
但一旦脚本被杀、变异没被还原，测试就成了**变异版本**的「绿」。）

**没有独立对比，我永远不会知道源码被改了。**

### 我自己踩了四次

| 次 | 怎么回事 |
|---|---|
| 1 | `finally` 没执行，`sandbox.py` 被留在变异状态 |
| 2 | 我为了**看进度**，在运行探针的**同一个终端**里发了另一条命令 —— 把探针杀了 |
| 3 | 我查**错**了备份目录名（查 security 探针的，不是 capability 的），据此误判「干净」 |
| 4 | 2026-09-14：**又一次**在同一终端里发了别的命令，杀掉后台探针 ——
`app/nodes/tool.py` 留下变异（`default="calculator"`） |

> **讽刺之处**：纪律是我自己定的，然后我第四次踩了同一个坑。
>
> **这恰恰说明为什么「每抽一个接口都配反向验证」不能靠自觉 ——
> 要靠工具**（sidecar 备份、`_restore_guardprobe.py`），**因为人一定会忘**。

### [重要] 第四次那回，两道防线都真的生效了

这是它们**第一次在实战里被用到**，所以值得记下实际发生了什么：

| 防线 | 实际表现 |
|---|---|
| **sidecar 备份** | 下一次运行**拒绝启动**（`RESULT=FAIL (unclean previous run)`）|
| **逐文件对比** | 报出 `app/nodes/tool.py : DIFFERS`，其余 6 个 `SAME` |

> **关键细节**：第一次运行留下的 `_probe.txt` 里
> **只有 traceback、没有任何 case 输出** ——
> 因为 Python 的 stdout 重定向到文件时是**块缓冲**的，崩溃时缓冲区丢了。
> 所以「没输出」不是「没跑」，**不能用输出去推断探针没运行过**。
>
> 判断「探针跑没跑」要看**备份目录在不在**，不要看输出。

### 正确的后台启动方式（本次修的）

`Start-Process` 让子进程**真脱离 shell**，之后用**别的终端命令**也不会碰到它：

```powershell
Start-Process -FilePath 'd:\AI_LLM_Project\venv_d\Scripts\python.exe' `
  -ArgumentList '-u','_guardprobe_capability.py' `
  -RedirectStandardOutput 'H:\agent_scaffold\_probe.out.txt' `
  -RedirectStandardError 'H:\agent_scaffold\_probe.err.txt' `
  -NoNewWindow -PassThru
```

**`-u`（无缓冲）是必需的** —— 否则输出文件在进程结束前是空的。
之前那回就是**重定向了但没有 `-u`**，所以看不到进度。

### 探针工具自己出过的六个问题（重造时要记得）

| # | 问题 | 修法 |
|---|---|---|
| 1 | **sidecar 用基名命名** → `registry.py` / `settings.py` 重名 → **静默跳过**（退出码仍是 0！） | 用扁平化相对路径（`tools__registry.py`）；歧义**显式报警 + 非零退出**（`RESULT=INCOMPLETE`） |
| 2 | **探针把「当前内容」当成「原始内容」** → 上次被杀留下的变异成了新基线 → 对**脏树**签发健康证明 | 备份目录存在时**拒绝启动** |
| 3 | 不可证伪的测试（见上） | 反向验证抓出来 |
| 4 | **`text=True` 用父进程的编码解码子进程输出** → 在 `-X utf8` 下读取线程死在第一个非 ASCII 字节，**探针一个 case 都没跑就退出** | 两侧都钉死 UTF-8（子进程 `PYTHONIOENCODING`，父进程 `encoding=`/`errors="replace"`） |
| 5 | **`subprocess.run(timeout=N)` 杀不掉卡住的测试** → 它的孙进程握着 stdout 管道，`communicate()` 永远等不到 EOF。实测：一个 240s 超时的 case **挂了 25 分钟以上**，进程树里两个 `pytest` 进程 0% CPU | 用 `Popen` + 超时后 `taskkill /F /T /PID`（**整棵树**）+ 有界 `communicate(timeout=30)` 排空管道 |
| 6 | **case 因为「变异载荷自己 import 崩」而变红** → 探针把它记作 `OK`（守卫承重），而瞄准的那句断言**根本没跑到**。实测：`llm node reaches past the gateway` 的载荷里写着已不存在的 `app.ai.*`（`6ebe52e` 改目录后没跟着改），于是它**停摆一个月**，同时在 `118/118` 里充数 | 载荷里的模块路径必须跟着目录一起搬（已改）。**注意它是第 5 条的反面**：第 5 条是「该红不红」，这条是「红得不是地方」 |

> 「一份对脏树签发的健康证明，**比没有检查更糟**。」
>
> 第 4 条推广开来：**探针的行为不能依赖「它是被怎么调用的」**。
> `-X utf8` 是一个完全正常的启动方式，而它让工具默默失效了。
>
> 第 5 条推广开来：**「设了超时」不等于「超时能生效」**。
> 这一条尤其值得单独看 —— 探针**本来就把 `hang` 当作合法的正向结果**
> （「测试挂住 = 守卫是承重的」），所以超时失效时它不会报错，
> 只会**永远等下去**。**一个把「挂住」算作成功的工具，必须能真的杀掉挂住的进程。**
### [重要] 第 7 个不是探针，是**文档检查器**：它报了 `0 problems`

本刀写了一版收尾检查（emoji / 死链 / 迁移编码 / 残留），
它在 emoji 一项上**报 `0 problem(s)`，而当时文档里还有 4 处**。
后来用**另一份独立写的**检查（不按范围匹配，而是**逐个列出要删的码点**）
才发现。

**这比探针的问题更值得警惕**，因为它不是「工具坏了」，而是
**「工具说全绿」**：

| | 表现 |
|---|---|
| 探针失效 | 什么都不输出 → 至少**看得出**不对 |
| **检查器失效** | **打印 `RESULT=PASS`** → 没有任何信号 |

**判据**：

1. **范围匹配的检查必须自己也能被证伪** ——
   写一个「本应被匹配到」的样本，确认它真的报出来
2. **收尾检查用两种独立写法**：一种按**码点白名单**（精确），
   一种按**区间扫描**（宽）。两者都说干净才算干净
3. 清理类操作**不要只跑一次就宣布完成** —— 第 2 遍要能报出
   「已经不剩任何东西」，而不是「0 problems」（两者输出一样）

## 4. [最重要] 不要轮询终端（会把任务杀掉）

### 症状

把长任务放后台后，又用**同一个终端**去轮询 ——
新命令把还在跑的进程**打断了**，表现为「安装跑到一半就停」。

### 规则

长任务必须**完全脱离终端**：

```powershell
Start-Process -FilePath 'pwsh' `
  -ArgumentList '-NoProfile','-File','<script.ps1>' `
  -WindowStyle Hidden -PassThru
```

之后**只读日志文件**（`read_file` 不碰终端），
**绝不在长任务运行期间用终端轮询**。

### `-NoNewWindow` **不够** —— 它共用控制台，会被 Ctrl+C 打死（2026-09-14）

`-NoNewWindow` 让子进程**共用父控制台**，所以调用方（工具/终端）发出的
**控制台中断（Ctrl+C）会送达子进程**。实测：

```
Traceback ... File "subprocess.py", line 1644, in _communicate
    self.stdout_thread.join(self._remaining_time(endtime))
KeyboardInterrupt
```

一个跑了 69/104 个用例的探针就这样在**没有任何报错**的情况下退出了 ——
输出文件停在 69 行，没有 `RESULT=` 行。

**修法**：用 `-WindowStyle Hidden`（**自己的控制台**），不要 `-NoNewWindow`。

```powershell
Start-Process -FilePath '<python>' -ArgumentList '-u','<script.py>' `
  -RedirectStandardOutput '<out>' -RedirectStandardError '<err>' `
  -WindowStyle Hidden -PassThru
```

**验证方式**：启动后先发一条无关的终端命令，确认进程仍然存活 ——
不要假设「脱离了」。这一条本刀实测过：`probe alive: True` 才算成功。

### 注意： 「重定向到文件再看」对 Python 脚本**不成立**

Python 写文件是**全缓冲** —— 进程结束前文件是空的。

**所以「读文件看进度」在这里没用，只能等。**

**修正**：加 `-u`（无缓冲）它就有用了，而且**这是必须的**，
否则连「探针是否还在跑」都看不出来。

## 5. [最重要] 同一个 bug 第二次修复失败 → 停止改代码

### 故事

`restart_backend.ps1` 想在终端显示进度，但服务启动后脚本会挂起。
我**连改 3 次**，每次都能编出一个「看起来说得通」的解释，然后继续改。

**结果**：把正在用的服务弄停了两次（中间那些方案**自检通过**但进程
随脚本退出而死，所以端口是空的）—— 用户在两次「修好了」之后发现服务没了。

### 转折点

**写了一个 20 行的最小探针**（只做一件事：启动一个服务，打印 PID），
分别裸跑和管道跑。

**第五分钟就得到了答案。**

### 规则

| 场景 | 做法 |
|---|---|
| 能一次说清机制 | 直接改真代码 |
| **说不清** | **先写最小复现** |
| 同一个 bug 第二次修复也失败 | [重要] **必须停下来写探针** |

**为什么真代码会误导**：它身上挂着自检、i18n 探测、端口清理、文件写入……
**每个无关因素都能给出一个貌似合理的错误解释。**

**探针脚本用完立刻删**（别留在仓库里）。

## 6. [重要] 未验证的前提会自我复制

### 故事

`restart_backend.ps1` 的注释写着「the console here mangles UTF-8」，
所以它一直把结果写进文件 —— **代价是脚本完全看不到进度**。

**实测**（pwsh 7.6.6，`[Console]::OutputEncoding` = gb2312）：

```powershell
Write-Host "PWSH 中文：开始 / 大模型 / 提示词"          # 正常
python -c "print('PYTHON 中文：开始 / 大模型 / 提示词')"  # 正常
```

**两个都正常显示。** 那个假设大概来自 powershell 5.1 时代。

### [重要] 更糟的是它扩散了

从「这个脚本写文件」扩散成一条**更宽的规则**：
「不要向控制台 print 非 ASCII」—— **而那条同样没被验证过**。

### 规则

**写进注释/文档的「环境限制」要附实测命令与结果。不确定就标注「未验证」。**

## 12. [重要] 读-改-写整文件 + 过期读取 = **静默回退别人的修改**

2026-09-14 收尾时实测到的事。这一节的脚本，一律是这个形状：

```python
text = path.read_text()          # 读
text = text.replace(old, new)    # 改
path.write_text(text)            # 写回整文件
```

**这个形状在「同一次会话里另一个工具刚改过这个文件」时不安全。**

实测：`docs/target/reuse.md` 的 emoji 已经被一个脚本清掉（脚本自检报
`remaining emoji: []`），后来又跑另一个脚本往同一文件插入新章节 ——
**读到的却是清理之前的版本**，于是**整文件写回时把 emoji 全带回来了**（12 行）。

**没有任何一步报错**，两个脚本各自都「成功」了。文件只是变回了旧样子。

### 判据

| 症状 | 含义 |
|---|---|
| 自己刚改的内容不见了 | 可能是**别的写入被回退**了，不是自己没写 |
| 自检说「已完成」而文件里没有 | 要么没写进去，要么**后被整文件写回覆盖**了 |

### 规则

1. **改完一个文件要复核整个文件的关键不变量**，不能只复核「我这次改的那一处」
   —— emoji 清理、章节存在性、链接，一起看
2. **整文件写回的脚本，写之前先把自己关心的不变量记下来，写完逐个断言**
   （本节的两个脚本就是这么做的，见 `docs/lessons/process.md` §13 的扫描器）
3. **收尾扫描要用两种独立方法**，并且**断言两种方法的结论一致** ——
   不一致本身就是信号

## 13. [重要] 过宽的检查器不是更严格的检查器，是**坏掉的**检查器

同一天的第二件事。写了一个「emoji 区间扫描」，把 `U+2190`–`U+21FF`
（箭头）也划进了 emoji 区间 —— 而**同一段代码的注释里写着「箭头是允许的」**。

结果：**676 条假阳性**，而且因为两个方法的计数永远不同，
「两种方法一致」这条断言**永久失效**。

**真正的 emoji 只有 1 个**（`docs/lessons/process.md` 里一个 ``U+2605`），
藏在 676 条噪声里。

### 判据

| | 效果 |
|---|---|
| 精确方法（码点白名单） | **找出了那 1 个真问题** |
| 过宽的区间扫描 | 676 条噪声，**真问题被淹没** |

**推广**：检查器的价值是**信噪比**，不是覆盖面。
一个「什么都报」的检查器会被忽略，**等于没有检查**。

### 而且：``U+2605` 是**最容易回来**的那一个

本日之内，``U+2605`（U+2605）从三个不同的文件里被清掉过。
它和 ``U+26A0` `U+FE0F`` / ``U+2705` 不同 —— 它**读起来像「强调」而不是「装饰」**，
所以写文档时会很自然地打出来。

**本项目的强调标记是 `[重要]` / `[最重要]`，状态是 `[x]` / `[ ]` / `[~]`。**
没有例外，包括「看起来像排版而不是 emoji」的那些。

## 8. 反向验证工具的正确形状

**重造一个探针时照这个做：**

| 要求 | 为什么 |
|---|---|
| **先写 sidecar 备份**，再动第一个文件 | 被 `kill -9` 时 `finally` 不执行 |
| sidecar 名用**扁平化相对路径**，不用基名 | 这个树里 `registry.py`/`settings.py` 重名 |
| **备份目录存在时拒绝启动** | 否则把变异当基线 |
| 歧义名**非零退出** | 「有些文件没检查」≠「干净」 |
| 子进程加 `timeout`，挂起算**单独结果** | 强制 in-process 的用例里，挂起**恰恰是边界承重的证明** |
| 支持**按测试名过滤** | 全跑几分钟，迭代时用不了 |

**用法**：

```powershell
Set-Location h:\agent_scaffold\backend
& 'd:\AI_LLM_Project\venv_d\Scripts\python.exe' _guardprobe_capability.py
# RESULT=PASS (0 problems) + SOURCES_RESTORED=True（用例数见 current/status.md §汇总）

& 'd:\AI_LLM_Project\venv_d\Scripts\python.exe' _guardprobe_capability.py test_run_retention.py
```

**新增用例别另建探针** —— 第二个备份目录就是第二个要记得检查的东西，
**忘记检查已经导致过一次假的「干净」结论**。

## 10. [最重要] 缓存的伪证：`NOT caught` 不一定是你以为的那个原因

**症状**：探针报「这个守卫是装饰品」。**但它是好用的** ——
单独跑那个用例通过，只有全量跑才失败。

> 2026-09-14 真实发生。排查花了三轮，最后查的是 **pytest 的源码**。

### 根因：pytest 断言重写的 `.pyc` 缓存键是 `(整秒, 字节数)`

```python
# _pytest/assertion/rewrite.py（pytest 9.0.3 实测）
mtime = int(source_stat.st_mtime) & 0xFFFFFFFF     # ← 注意是 int()，整秒
size  = source_stat.st_size & 0xFFFFFFFF           # ← 精确字节数
```

两个键**都**相同 → 缓存命中 → pytest **直接 import 旧的 `.pyc`** →
**源码根本不读** → 变异从未执行 → 报「未抓到」。

而那一次是：

| | 长度 |
|---|---|
| anchor `"columns": sorted(` | **30** |
| replacement `"columns": [],  # ` | **30** |

**字节数一模一样**，加上写入落在与上次记录相同的整秒内 → 两个键全中。

### 修法

变异文本长度与原文相同时，**补一个换行**：

```python
mutated = source.replace(case.anchor, case.replacement, 1)
if len(mutated) == len(source):
    mutated += "\n"        # 空行在 Python 里是惰性的
```

mtime 那一半**在探针里没法可靠地修**（取决于基线运行花了多久）。
但缓存命中要求**两个键都相同**，所以改掉一个就够了。

### [重要] 这是本项目第三次遇到同一类问题

| # | 场景 | 伪证的来源 |
|---|---|---|
| 1 | `describe()` 覆盖率测试 | `KNOWN_SECRETS` 成员太少，覆盖循环要靠 monkeypatch 追加名字才承重 |
| 2 | SSE 回放窗口响应头 | 断言两边来自**同一个源**（都硬编码了） |
| 3 | **本条的 `NOT caught`** | **变异根本没运行** |

### 推广：`NOT caught` 有两种完全不同的原因

```
1. 守卫真的没起作用          → 改代码
2. 探针的变异没被执行        → 改探针
```

**判别向**：全量跑失败、单独跑通过 → 第 2 种。

## 11. 一堆**互不相关**的测试同时失败 → 先怀疑文件被改坏了

2026-09-14 任务 2.6 收尾时的真实事件。

**症状**：跑全量，**26 个失败**，而且散在 `test_secret_provider`、
`test_tool_capability`、`test_run_retention` 这些**我根本没碰过的文件**里。

**我当时的第一反应是错的**：开始怀疑「进程级 store 泄漏到其他测试」。
但泄漏不会让 26 个不相关的用例失败。

**去读第一个失败的完整 traceback，一眼就看到了**：

```
File "backend/app/db/run_store.py", line 3
  This is the platform's implementation...
  ^
SyntaxError: unterminated string literal
```

**根因**：那个文件的第一行被改坏了。原文是

```
"""The database-backed :class:`~app.runtime.runs.RunStore`.
```

变成了

```
zhanbidatabase-backed :class:`~app.runtime.runs.RunStore`.
```

`"""The `（7 个字符）被替换成了 `zhanbi`（6 个字符）——
一个来路不明的输入法/粘贴残留。文件**其余 141 行完好**。

因为它是**语法错误**，任何 import 到它的代码全部炸；
而它是 `build_run_store` 里那句惰性 import 的目标，
所以启动期间就会炸 —— 于是所有走 lifespan 的测试一起失败。

### 教训

| 现象 | 该想的 |
|---|---|
| 失败**集中在我改过的东西** | 逻辑 bug |
| 失败**散在我没碰过的东西** | **先怀疑文件/环境被破坏了** |

**动作**：**编一遍整个树**再继续。80 个文件 `py_compile`，一秒钟出结果：

```powershell
python -c "import pathlib,py_compile; [py_compile.compile(str(f),doraise=True) for f in pathlib.Path('app').rglob('*.py')]"
```

> 这类损坏**不是逻辑错误，读代码读不出来** ——
> 而且它伪装成一堆「我破坏了别的功能」的假象，最耗时间。

---

**修代码之前，先确认变异真的发生了。**
把「变异确实写进了文件」当作需要验证的前提，而不是假设。
